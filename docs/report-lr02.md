## 2. Контракт і CP-01

Request: [CreateIncidentRequest](../src/SecureLab.Api/Presentation/Contracts/CreateIncidentRequest.cs). Response: [CreatedIncidentResponse](../src/SecureLab.Api/Presentation/Contracts/CreatedIncidentResponse.cs). Обробник: [Lab02Endpoints](../src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs).

| Поле / правило | Умова | Порушення |
|---|---|---|
| title | Не порожній після Trim; початкова довжина ≤160 | 400, errors.title |
| description | Не порожній після Trim; початкова довжина ≤4000 | 400, errors.description |
| severity | Enum.TryParse без урахування регістру та Enum.IsDefined | 400, errors.severity |
| occurredAtUtc | Обов'язковий DateTimeOffset; ≤now+5 хвилин, now зафіксований один раз | 400, errors.occurredAtUtc |
| UTC | Після перевірки ToUniversalTime перед записом | +03:00 приймається та перетворюється в UTC |
| High/Critical | Description після Trim має щонайменше 40 символів | 400, errors.description |
| Предметний конфлікт | Такий самий після Trim title з тим самим регістром у New, Triaged, InProgress або Resolved | 409 Problem Details; Closed не блокує |

Рядки нормалізуються через Trim по одному разу. Обмеження максимальної довжини перевіряє початкові значення, тому зайві пробіли не дозволяють обійти 160/4000. Усі помилки полів збираються у `Dictionary<string, string[]>`; за наявності помилок відповідь формується до доступу до БД та створення entity. Перевірені значення використовуються і для пошуку конфлікту, і для збереження.

Маршрут: **JSON → request DTO → серверні перевірки → перевірка конфлікту → entity → SaveChangesAsync → response DTO + 201 та Location**. Некоректні поля повертають 400; дубль незакритого інциденту — 409. Наявний маршрут GET за неіснуючим id повертає 404. Усі три типи помилок мають `application/problem+json`, `title` і `status`; 400 також має `errors`, а 404/409 — `detail`. У збережених відповідях немає SQL, stack trace, connection string чи назв внутрішніх класів.

**CP-01.** `Enum.TryParse` приймає числовий рядок `"7"`, але такого елемента немає в enum. `Enum.IsDefined` відхиляє його; фактичний результат — 400 з ключем severity. Перевірка HTML select не захищає API, тому що клієнт може надіслати довільний HTTP-запит.

Id, OwnerUserId, Status, CreatedAtUtc і UpdatedAtUtc відсутні у request DTO. Сервер призначає новий Guid, навчального власника Alice, статус New та власний час. У контрольному запиті передано чужий ownerUserId, id і status=Closed: створено інший id `92916798-cf68-431b-a964-692f5c4af3bf`, статус New. GET створеного запису показав «Аліса Коваль». Вхідний час `2026-09-01T13:00:00+03:00` збережено як `2026-09-01T10:00:00+00:00`. Докази: [T-01](evidence/fixed-T01.txt), [GET після створення](evidence/fixed-CP01-details.txt), [невалідний enum](evidence/fixed-T02-enum.txt).

Першопричина в `src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs`, методі `MapLab02Endpoints`, обробнику GET `/api/incidents/search`: у цьому commit рядки **20–21** складають SQL з q та order, рядок **22** виконує `FromSqlRaw(sql)`. ### CP-02: пояснення першопричини

Query string прив'язувався до параметра q; його значення конкатенувалося всередині SQL-літерала. У сценарії C апостроф закривав літерал, логічна частина змінювала умову відбору, а коментар відсікав решту тексту. База отримувала вже зібрану команду без окремих параметрів. Тому B не знаходив записів, а C повертав записи, які не відповідали буквальному значенню пошуку. Легітимний апостроф також ламав SQL-синтаксис і спричиняв 500. Заборона апострофів або одного слова не усуває змішування коду й даних і заважає коректним іменам.

### CP-03: механізм виправлення

Пошук переписано на LINQ із `EF.Functions.ILike` для Title та Description. Шаблон передається параметром, а не приєднується до SQL. Escaping виконується в порядку `\`, `%`, `_`, з явним escape-символом: це забезпечує буквальний підрядок, а не просто захист SQL. Легітимний апостроф приймається як звичайний символ.

sortBy перевіряється до виконання запиту: дозволено лише createdAtUtc, severity, status. Відсутнє або порожнє значення обирає createdAtUtc. Порядок — CreatedAtUtc DESC; severity Critical→High→Medium→Low; status New→Triaged→InProgress→Resolved→Closed. У кожній гілці додано Id ASC, потім Take(50). Ранги задаються явними умовами, бо назви enum зберігаються в БД як рядки й алфавітний порядок неправильний. Невідомий sortBy повертає 400.

У журналі виконання після fix спостерігалися окремі параметри `@pattern`, `@pattern0`, `@p`; значення приховано, sensitive-data logging не вмикали. Для SQLi-вводу база тепер шукає буквальний підрядок, тому результат порожній. [Стислий доказ параметрів](evidence/query-mechanism.txt).

Security diff відтворюється так:

```powershell
git diff c5a6f5e1108d6c4e7d02c56303e3708cac658bdf 0c6ebf8259e65566837e80302e24b68a06e8782b -- src tests
```

## 5. Обмеження і висновок

Перевірка AnyAsync до SaveChangesAsync повертає зрозумілий 409 за звичайного повторного створення, але два одночасні POST можуть обидва пройти попередню перевірку. У промисловому застосунку потрібне узгоджене обмеження БД або транзакційне рішення. У ЛР2 migration та унікальний індекс не додавалися відповідно до методички.

Навчальний власник Alice ще не є перевіреним authenticated principal; це предмет ЛР3. Захист пошуку не замінює авторизацію, повний аудит усіх маршрутів, обмеження ресурсів і політику production logging. Take(50) є лімітом результатів, а не реалізацією пагінації. Перевірки DTO використовували правильний JSON і правильні JSON-типи; поведінка зіпсованого JSON у цьому виконанні окремо не перевірялася.

Отримано серверний контракт створення, передбачувані відповіді 400/404/409 і пошук, у якому значення не змінює структуру SQL. Регресія підтвердила нормальну роботу апострофів і буквальних спецсимволів, збереження підсумку ЛР1 та правильне сортування. Заявляється рівень «Добре»; завдання T-10 і A-02 відмінного рівня не заявляються.
