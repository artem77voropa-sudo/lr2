# ЛР2: покрокова демонстрація у VS Code

Автор: Воропаєв Артем Максимович, КБ-41. Рівень: «Добре».

Це маршрут для пояснення власного проєкту та створення скріншотів після виконання роботи.
Кожен крок можна проходити разом з асистентом: виконати дію, перевірити результат, зробити скріншот, перейти далі.
Збережені HTTP-відповіді вже є в `docs/evidence`; нові скріншоти їх доповнюють.

## 1. Відкрити власний проєкт і показати версію

У VS Code: File → Open Folder → `C:\dev\securelab`.
Відкрити Terminal → New Terminal. Команди виконуються в PowerShell із кореня проєкту:

```powershell
git status --short
git branch --show-current
git log --oneline --decorate -6
dotnet --version
```

Очікування: гілка `lab/2-input-sqli`, тег `v0.2.0`, .NET 10.0.402, чисте дерево.
Скріншот 01: дерево файлів і термінал із гілкою/історією/SDK.
Пояснення: ЛР2 продовжує власну ЛР1; стани до й після виправлення збережені окремо.

## 2. Підняти PostgreSQL

Відкрити Docker Desktop і дочекатися готовності. У VS Code:

```powershell
docker compose --env-file infra/.env.example -f infra/compose.yaml up -d --wait
docker compose --env-file infra/.env.example -f infra/compose.yaml ps
```

Очікування: `secure-lab-postgres-1`, стан healthy. Скріншот 02: список контейнерів і healthy.

## 3. Показати збірку й тести

Перед тестами ручний API має бути зупинений. Якщо він запущений у терміналі — Ctrl+C у тому терміналі.
Початковий стан уже відновлено асистентом. Для повторення з відомого seed команда reset очищує поточні навчальні записи;
спочатку збережи потрібні відповіді й скріншоти.

```powershell
dotnet build SecureLab.sln -c Release
dotnet test tests/SecureLab.Api.Tests -c Release
```

Очікування: збірка без помилок; **42 тести успішні**. Скріншот 03: кінцеві підсумки команд.
Пояснення: перевіряємо реальний API й PostgreSQL; тимчасові записи тестів очищуються в finally.

## 4. Запустити API

Скріншот 04: журнал запуску. Не показуй локальні файли з власними секретами.

## 6. CP-01: коректний POST і захист серверних полів

Виконати блок **T-01 / CP-01**. Очікується 201, заголовок Location і response DTO.
Показати, що надіслано status=Closed та підставний id, але отримано **New** та інший id.
Час +03:00 у запиті перетворено на UTC у відповіді.
Відкрити URL із Location через браузер або GET: ownerDisplayName — **Аліса Коваль**.
Скріншоти 06 і 07: запит/201 та GET створеного запису.

Якщо T-01 уже виконували, повтор дасть 409. Для нового 201 зміни title в T-01 і відповідному T-03 на новий однаковий текст.
Для демонстрації без редагування файлів скористайся ще не використаним заголовком із початкового файлу.
Пояснення: request DTO містить лише чотири поля; серверні поля не зв'язуються з entity.

## 7. Показати 400, 409 і 404

Послідовно виконати:

1. T-02 severity `"7"`: 400 і errors.severity.
2. T-02 required: 400 і ключі title/description/severity/occurredAtUtc.
3. T-02 відсутня/майбутня дата: 400 і occurredAtUtc.
4. T-03 після T-01: 409 з поясненням конфлікту.
5. T-06: 404 з повідомленням «Інцидент не знайдено».

Скріншоти 08–12: статус, Content-Type і тіло відповіді.
Пояснення: 400 — неправильні дані; 409 — конфлікт правильного запиту з поточними даними; 404 — відсутній ресурс.
Усі відповіді мають application/problem+json; внутрішніх SQL/stack trace в них немає.
Для меж довжин додатково виконати два останні POST: 161 символ title та 4001 символ description → 400.

## Після демонстрації

Зупинити API через Ctrl+C. За потреби зупинити тільки власний PostgreSQL:

```powershell

```

Для захисту вміти пояснити: DTO проти entity; TryParse проти IsDefined; 400/404/409;
UTC; cross-field; параметризацію проти escaping; allowlist; обмеження AnyAsync при одночасних запитах.
